# GSQ-RCO 原版 GGUF → .ninfer 模型转换指南

> 把 HuggingFace 上的 GSQ-RCO 量化 GGUF 转成 NInfer 引擎可加载的 `.ninfer` 容器。
> 转换在 **CPU 上进行，不碰 GPU、不占显存、不重量化**——GSQ 的逐张量量化块原样导入，
> 只做张量重排与元数据封装。
>
> 本仓库实测：**12GB GGUF → 11.6GiB .ninfer，全程 63.3 秒**（24 核 CPU + NVMe）。

## 1. 变体与文件对照

GSQ-RCO 量化有两条权重线，配方与转换路线完全相同，按需选择：

| 变体 | S 档 GGUF 文件名 | 配套元数据（5 件套）来源 | 说明 |
|---|---|---|---|
| **ISTA**（本仓库实测，质量更优） | `Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf` | `Qwen/Qwen3.8-27B` | 上游 WikiText-2 PPL 7.071 |
| **Swift**（官方 50 系软件包默认） | `Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf` | Swift 变体自己的仓库 | 官方 XXS/S 两档即由它转出 |

GGUF 下载仓库：`ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF`（ISTA）及 Swift 对应仓库（HuggingFace）。

档位与文件名后缀：

| 档位 | 主体量化 | 权重体积 | 特点 |
|---|---|---|---|
| IQ3_XXS | IQ3_XXS | ~9.4GiB | 更小，上下文可更长（50 系官方 160K 档） |
| **IQ3_S** | IQ3_S | ~11GiB | **质量更好且解码反而快 5–6%**（50 系官方实测），代价是少 32K 上下文 |

`-mtp` 后缀 = MTP 预测头已合并进 GGUF，转换走 `text,mtp` 组件即可，**不需要**另外下载独立的
`mtp-*.gguf` 文件。`mmproj-*.gguf` 是视觉投影器，本路线（text）用不上。

## 2. 哈希校验（不要跳过）

转换器和 vcpkg 一样有哈希门禁，且网络传输损坏的排查全靠它。下载完先对 SHA256：

```bat
certutil -hashfile "D:\...\Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf" SHA256
```

本仓库实测输入的 SHA256（可与 HF 页面 LFS 记录核对）：

```
58fd826723939933dc86f45b7fe04545cbc2de1c70f6fe2cdd3858c87a98c12f
```

> ⚠️ 国内下载经验：HF 直连不稳时用镜像 `https://hf-mirror.com/<repo>/resolve/main/<file>`；
> 下载完成后**一定**校验，镜像偶发的截断文件只在哈希比对时暴露。

## 3. 元数据 5 件套

转换需要 GGUF 之外的配置与分词器（放入一个目录，下称 `<metadataDir>`）：

```
config.json  tokenizer.json  tokenizer_config.json  chat_template.jinja  generation_config.json
```

ISTA 配 `Qwen/Qwen3.8-27B` 的；Swift 配 Swift 仓库的。下载：

```bash
mkdir -p D:/ninfer/convert-input/Qwen3.8-27B && cd D:/ninfer/convert-input/Qwen3.8-27B
for f in config.json tokenizer.json tokenizer_config.json chat_template.jinja generation_config.json; do
  curl -sL -o "$f" "https://hf-mirror.com/Qwen/Qwen3.8-27B/resolve/main/$f"
done
```

（校验：`config.json` 开头应是 `{"architectures": ["Qwen3_5ForConditionalGeneration"]...`；tokenizer.json 约 12.8MB。）

## 4. 转换环境

需要源码仓库（转换器在 `tools/convert/`，软件包不附带）+ 64 位 Python 3.11 venv：

```bash
py -3.11 -m venv D:/ninfer/convert-venv
D:/ninfer/convert-venv/Scripts/python.exe -m pip install numpy huggingface_hub
D:/ninfer/convert-venv/Scripts/python.exe -m pip install torch --index-url https://download.pytorch.org/whl/cpu
```

- torch 用 **CPU 版**（`--device cpu` 转换路线），不需要 CUDA 版 PyTorch
- 这条 text+mtp 原样导入路线**不需要** `gguf` Python 包
- 外部计算依赖只有 PyTorch + NumPy
- 磁盘要同时放下：GGUF（12GB）+ 输出 .ninfer（11.6GiB）

## 5. 执行转换

在**源码仓库根目录**执行（转换器以 `tools.convert` 模块方式调用）：

```bash
cd /d/ninfer/src
D:/ninfer/convert-venv/Scripts/python.exe -u -m tools.convert \
  --model "D:/ninfer/convert-input/Qwen3.8-27B" \
  --recipe qwen3_8_27b_gguf \
  --source "gguf=D:/ai_models/models/qwen/Qwen3.8-27B-GSQ/Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf" \
  --components text,mtp \
  --proposal \
  --device cpu \
  --rows-per-chunk 512 \
  --name Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp \
  --out "D:/ninfer/converted-models/Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.ninfer"
```

| 参数 | 说明 |
|---|---|
| `--model` | 元数据目录（5 件套所在），**不是** GGUF 文件 |
| `--recipe qwen3_8_27b_gguf` | 保留原 GGUF 量化块的 Qwen3.8-27B 配方 |
| `--source "gguf=..."` | 指向 GSQ GGUF 文件 |
| `--components text,mtp` | 导入文本权重与内嵌 MTP |
| `--proposal` | 额外保存供 `--lm-head-draft` 的精简词表预测头；读取仓库内 `tools/freq_corpus/fixtures/ranking/ranking.train.counts.i64`，无需另跑校准。不是 MTP 的必需条件（始终关闭 `--lm-head-draft` 可省略） |
| `--device cpu` | CPU 转换，不依赖 CUDA 版 PyTorch |
| `--rows-per-chunk 512` | 分批行数，与推理 prefill 无关 |
| `--name` | 制品元数据名（服务端 `--model-id` 可再覆盖对外名） |
| `--out` | 输出 .ninfer 路径 |

**输出**：`.ninfer` 本体（实测 12,494,820,096 字节 ≈ 11.6GiB）+ `.ninfer.conversion.json` 转换报告
（张量清单/来源/耗时；本仓库 `conversion/` 有脱敏样例）。输出路径已有同名文件时转换器拒绝覆盖，
换文件名或清目录重跑。

成功标志：终端输出 `wrote D:\...\xxx.ninfer: 848 objects, 1 files, 63.3s`（秒数因机器而异）。

## 6. 本仓库实测的量化构成（conversion 报告摘要）

843 个张量的逐张量混精分配（GSQ/RCO 的特色——不均匀量化，按张量敏感度分配精度）：

| 模块 | 量化格式 |
|---|---|
| 主体（64 层，hidden 5120） | `gguf_iq3_s` |
| attention key / mlp down | `gguf_iq4_xs`（更不敏感，给低一点） |
| MTP 模块（input_projection 等） | `gguf_q6_k` |
| proposal 头（131072×5120） | `gguf_q4_k` |
| 各类 norm | bf16 |

架构信息：`Qwen3_5ForCausalLM`，64 层，GDN 线性注意力 + 全注意力混合（`layer_types` 前 3 层
linear_attention / 第 4 层 full_attention 交替），词表 248,320，原生窗口 262,144。

## 7. 常见问题

**Q：转换报哈希/读取错误？**
先跑第 2 节的 SHA256 校验。最常见原因是镜像下载截断，或拿错了变体文件（Swift/ISTA 文件名很像）。

**Q：转换慢吗？**
不做任何重计算，纯拆包重排。24 核 + NVMe 实测 63 秒；老机器估计 5–15 分钟也正常，看磁盘。

**Q：`.ninfer` 体积为什么和 GGUF 不一样？**
封装时重排张量布局并补充引擎辅助信息，大小会变（本例 12GB→11.6GiB）；量化精度不变。

**Q：能转 IQ3_XXS / IQ4 / 更高档吗？**
能，`--recipe` 同一条，`--source` 换对应档位的 GGUF 即可。50 系官方包的 XXS 档就是同路线转的。
更高档（IQ4_XS 及以上）体积超出 16GB 卡的实用范围，上下文会急缩。

**Q：转换出来的模型和官方软件包里的一样吗？**
官方包的 Swift XXS/S 由同一条 `text,mtp + --proposal` 路线转出（作者文档明示）。本仓库转的是
**ISTA** 变体 S 档，权重不同（质量略优），其余等价。

**Q：要重新校准/转换吗？换显卡之后？**
不需要——`.ninfer` 与显卡架构无关，40/30/50 系通用；换卡只需重新校准引擎设备 profile。

## 8. 视觉组件转换（可选）

在文本版产物之外转一个支持图片/视频输入的制品（本仓库实测通过）：

**额外准备**（相比文本路线多 3 项）：

1. 视觉权重文件：`mmproj-Qwen3.8-27B-BF16.gguf`（931MB，与 GGUF 同在 GSQ 仓库/本地目录）
2. 元数据目录**多补 2 个文件**：`preprocessor_config.json`、`video_preprocessor_config.json`
   （都在 `Qwen/Qwen3.8-27B` 仓库根目录；少一个就 `FileNotFoundError`）
3. venv **多装一个包**：`pip install gguf`（mmproj 解析走官方 gguf 包；纯文本路线不需要它）

**命令**（其余与第 5 节完全一致）：

```bash
D:/ninfer/convert-venv/Scripts/python.exe -u -m tools.convert   --model "D:/ninfer/convert-input/Qwen3.8-27B"   --recipe qwen3_8_27b_gguf   --source "gguf=D:/.../Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf"   --source "vision=D:/.../mmproj-Qwen3.8-27B-BF16.gguf"   --components text,mtp,vision   --proposal --device cpu --rows-per-chunk 512   --name Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp-vision   --out "D:/ninfer/converted-models/Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp-vision.ninfer"
```

实测：58.3 秒，11.9GiB（1176 张量 = 文本版 843 + 视觉 333；视觉塔 BF16 原样导入，patch_embedding
Q6 / merger Q8 / attention Q4 的混精分配由配方自动处理）。

**运行注意**：`--vision` 启动后 `--cuda-memory-policy mixed/strict` 不可用（引擎限纯文本），
须改 `default` 策略 + `--kv-capacity auto`；上下文相应缩减（16GB 卡实测 48K 可稳启动，
64K 会 FATAL，见部署文档 7.6 与踩坑 #22/#24）。
