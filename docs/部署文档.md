## 2. 架构总览与显卡相关性判定

整套部署分三层，**显卡相关性完全不同**——这是理解整个方案的关键：

| 层 | 内容 | 与显卡架构的关系 | 换卡后 |
|---|---|---|---|
| **模型层** | `.ninfer` 权重（11.6GiB） | **无关**。GSQ 量化块原样导入，转换在 CPU 上进行 | **直接复用** |
| **引擎层** | `ninfer-serve.exe`（1.07GB） | **强相关**。内含特定架构的 SASS 机器码：sm_120a=50系 / sm_89=40系 / sm_86=30系 | 必须匹配架构，4080/4090 与 4070TiS 同为 sm_89 可共用 |
| **配置层** | 启动参数 / KV 上限 / 校准 profile | **相关**（显存大小与代际特性） | 重新校准 + 重测显存上限 |

原始来源关系：

```
Neroued/ninfer（引擎本体）
  └─ iamwavecut/ninfer-all（汇总线：3090/4090/5090/PRO 6000 分支整合）
       └─ Ryan-gsq/ninfer-16g-5070ti-5080-5090-qwen3.8-27b-gsq-rco（50系 16GB 软件包 + 部署文档）
            └─ 本项目（RTX 40 系适配：源码重编 sm_89 + 复现实测）
```

**40 系的核心障碍**：官方软件包里的 `ninfer-serve.exe` 只含 sm_120a SASS（作者用 `nvprune -arch sm_120a` 裁过），40 系加载即报错。好消息是仓库 CMake 原生支持 `CMAKE_CUDA_ARCHITECTURES=80/86/89/120a` 四档，40 系无需改任何源码，换个编译参数即可。

### 3.4 国内网络：三级回退下载器

整个部署约 200MB 依赖要从 GitHub 拉走，直连被墙、代理又不稳定（TLS 中途被掐是常态）。解决：`scripts/fetch-asset.bat`（本仓库附带），通过 vcpkg 的资产缓存机制接管全部下载：

```bat
vcpkg.exe install ... (环境变量)
set X_VCPKG_ASSET_SOURCES=x-script,D:\ninfer\fetch-asset.bat {url} {dst}
```

回退顺序：**本机代理直连 → gh-proxy.com 镜像 → 无代理直连**，30 秒无流量自动断线换路。
⚠️ 环境变量名是 `X_VCPKG_ASSET_SOURCES`（带 X_ 前缀），写成 `VCPKG_ASSET_SOURCES` 会静默失效（踩坑 #8）。

## 4. 步骤一：模型转换（GGUF → .ninfer）

### 4.1 获取原版 GGUF 并做哈希校验（关键习惯）

本仓库实测转换的输入：`Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf`（12,120,016,960 字节，12GB）
来自 HuggingFace `ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF`。

下载后**务必校验**，转换器的哈希门禁会拒绝任何字节级偏差：

```bash
certutil -hashfile "D:\...\Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf" SHA256
# 本仓库实测值（与 HF LFS 记录一致）：
# 58fd826723939933dc86f45b7fe04545cbc2de1c70f6fe2cdd3858c87a98c12f
```

`-mtp` 后缀表示 MTP 预测头已内嵌，转换走 `text,mtp` 组件即可，**不需要**另外的独立 mtp 权重文件。
（GGUF 头里同时带 tokenizer 元数据，但转换仍需要独立的配置文件，见下。）

变体对照（配方相同、权重不同）：

| 变体 | GGUF 文件名 | 配套元数据仓库 |
|---|---|---|
| ISTA（本仓库实测） | `Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf` | `Qwen/Qwen3.8-27B` |
| Swift（官方包默认） | `Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf` | Swift 自己的仓库 |

### 4.2 准备转换环境

```bash
# 元数据 5 件套（约 13MB；国内直连 HF 失败用镜像前缀 https://hf-mirror.com/）
mkdir -p D:/ninfer/convert-input/Qwen3.8-27B && cd D:/ninfer/convert-input/Qwen3.8-27B
for f in config.json tokenizer.json tokenizer_config.json chat_template.jinja generation_config.json; do
  curl -sL -o "$f" "https://hf-mirror.com/Qwen/Qwen3.8-27B/resolve/main/$f"
done

# venv + 依赖（torch 用 CPU 版，约 200MB）
py -3.11 -m venv D:/ninfer/convert-venv
D:/ninfer/convert-venv/Scripts/python.exe -m pip install numpy huggingface_hub
D:/ninfer/convert-venv/Scripts/python.exe -m pip install torch --index-url https://download.pytorch.org/whl/cpu
```

转换器本体在源码仓库的 `tools/convert/`（软件包不附带），所以要先 clone/解压源码（见 5.1）。

### 4.3 执行转换（源码仓库根目录下）

```bash
cd /d/ninfer/src
/d/ninfer/convert-venv/Scripts/python.exe -u -m tools.convert \
  --model "D:/ninfer/convert-input/Qwen3.8-27B" \
  --recipe qwen3_8_27b_gguf \
  --source "gguf=D:/ai_models/models/qwen/Qwen3.8-27B-GSQ/Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf" \
  --components text,mtp \
  --proposal \
  --device cpu \
  --rows-per-chunk 512 \
  --name Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp \
  --out "D:/ninfer/converted-models/Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.ninfer"
```

参数说明：`--proposal` 额外生成供 `--lm-head-draft` 用的精简词表预测头（依赖仓库内
`tools/freq_corpus/fixtures/ranking/ranking.train.counts.i64`，非 MTP 必需但与官方制品一致）；
`--device cpu` 全程不占显存；`--rows-per-chunk 512` 与推理无关。

**实测耗时：63.3 秒**（12GB 读入 → 843 个张量原样拆包重排 → 11.6GiB 写出，848 objects）。
转换是纯搬运（不重量化、不校准、不碰 GPU），速度取决于 CPU 和盘，没有"编译一小时"的必要心理准备。

产出两个文件：`.ninfer`（模型本体）+ `.ninfer.conversion.json`（转换报告，本仓库 `conversion/` 目录有脱敏样例）。
输出目录已有同名文件时转换器会拒绝覆盖。

## 5. 步骤二：源码构建 sm_89 引擎

### 5.1 获取源码

```bash
git clone --depth 1 --branch main --single-branch \
  https://github.com/Ryan-gsq/ninfer-16g-5070ti-5080-5090-qwen3.8-27b-gsq-rco.git D:/ninfer/src
```

（GitHub 连不上就下载 `archive/refs/heads/main.zip` 解压，构建和转换都不需要 git 历史。）

### 5.2 CMake 配置（相对官方 50 系流程只改一处）

官方 50 系参数是 `-DCMAKE_CUDA_ARCHITECTURES=120a -DNINFER_SM120_NATIVE=ON`；
40 系改为 **89**，并**去掉** `NINFER_SM120_NATIVE`（那是 120a 专属的 native 路线开关，
89 走默认的 mma.sync 兼容路径，CMakeLists 对 80/86/89 是一等公民支持）：

```bash
# 先初始化 MSVC 环境（vcvars64），再：
cmake -S D:/ninfer/src -B D:/ninfer/build -G Ninja ^
  "-DCMAKE_TOOLCHAIN_FILE=D:/ninfer/vcpkg/scripts/buildsystems/vcpkg.cmake" ^
  -DVCPKG_TARGET_TRIPLET=x64-windows -DVCPKG_MANIFEST_MODE=OFF ^
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES=89 ^
  -DNINFER_BUILD_APPS=ON -DBUILD_TESTING=OFF -DNINFER_BUILD_BENCHMARKS=OFF ^
  -DNINFER_DIRECTSTORAGE=OFF -DNINFER_D3D12_RESIDENCY=OFF ^
  "-DCUDAToolkit_ROOT=C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.4" ^
  "-DCMAKE_CUDA_COMPILER=C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.4\bin\nvcc.exe" ^
  "-DCMAKE_CUDA_HOST_COMPILER=<cl.exe 路径>" ^
  "-DCMAKE_C_COMPILER=<cl.exe 路径>" "-DCMAKE_CXX_COMPILER=<cl.exe 路径>" ^
  -DCMAKE_MAKE_PROGRAM="<ninja.exe 路径>"
```

实测配置耗时 123.4s（期间 vcpkg 会完成依赖安装）。

**两个模式要点**：
- `VCPKG_MANIFEST_MODE=OFF`（classic）：依赖已用 classic 装进 `vcpkg/installed/`。manifest 模式需要
  vcpkg 树里有 baseline 提交的 git 对象，tarball 版拿不到会报 `git show ... failed`（踩坑 #6）
- `NINFER_D3D12_RESIDENCY=OFF` / `NINFER_DIRECTSTORAGE=OFF`：与官方文档一致

### 5.3 编译 CUDA 算子（⚠️ 本机实测最重要的坑：OOM）

```bash
cmake --build D:/ninfer/build --target ninfer_ops -j 22   # ❌ 32GB 内存机器会失败
cmake --build D:/ninfer/build --target ninfer_ops -j 8    # ✅ 降到 8 路
```

共 653 个编译单元，nvcc 单任务峰值 2–4GB 内存。本机实测 **22 路并行在 [602/653] 处静默死亡**
（32GB RAM 被榨干，编译进程被系统杀掉，**日志里只有警告没有错误行**，极具迷惑性）。
降到 `-j 8` 后一次通过。ninja 支持断点续编，已编好的对象不会重编。

### 5.4 nvprune 裁剪 + 链接

```bash
# 裁掉冗余 PTX，防链接超 Windows PE 2GiB 上限（单架构构建保险起见仍做）
nvprune.exe -arch sm_89 build/src/ops/ninfer_ops.lib -o build/src/ops/ninfer_ops.pruned.lib
mv build/src/ops/ninfer_ops.pruned.lib build/src/ops/ninfer_ops.lib

cmake --build D:/ninfer/build --target ninfer-serve -j 8
# 产物：D:/ninfer/build/apps/ninfer-serve.exe（实测 1,067,316,224 字节）
```

一键脚本见仓库 `scripts/build-sm89.bat`（改开头的路径变量区即可用）、`scripts/resume-sm89.bat`（OOM 后续编）。

### 5.5 vcpkg 依赖安装（classic 模式完整流程）

```bash
# 1) vcpkg 树（tarball 解压即可，无需 git 历史）
# 2) vcpkg.exe：从 microsoft/vcpkg-tool 仓库 release 下载对应版本，放 vcpkg 根目录
# 3) 环境变量 + 安装
export PATH="/d/ninfer/tools/cmake443/bin:$PATH"
export X_VCPKG_ASSET_SOURCES='x-script,D:\ninfer\fetch-asset.bat {url} {dst}'
export HTTP_PROXY=http://127.0.0.1:7897 HTTPS_PROXY=http://127.0.0.1:7897   # 按自己的代理改
./vcpkg.exe install curl "ffmpeg[zlib]" pkgconf --triplet x64-windows --disable-metrics
```

实测约 40 分钟（大头是 ffmpeg 编译）。哪些包会卡下载见踩坑 #7/#9/#10——所有源码包都能
手动下载后放进 `vcpkg\downloads\`（文件名必须与 URL basename 一致，哈希对了直接命中缓存）。

## 6. 步骤三：运行目录组装

引擎 exe 不能单独跑，旁边要 60+ 个 DLL。三路来源，按优先级叠加：

| 来源 | 内容 | 说明 |
|---|---|---|
| 官方软件包 `engine/*.dll` | 宿主依赖全套 + **cublas64_13 / cublasLt64_13 / cudart64_13** + VC 运行库 | CUDA 13 运行库与显卡架构无关，40 系直接用 |
| 自编 vcpkg 产物 `vcpkg/installed/x64-windows/bin/*.dll` | curl / ffmpeg 全家桶等 10 个 | **叠加在官方包 DLL 之上**（后复制者生效），保证与我们编译的 exe ABI 一致 |
| 自编 `build/apps/ninfer-serve.exe` | sm_89 引擎本体 | 替换包内 sm_120a 版 |

```bash
mkdir -p D:/ninfer/runtime/engine
cp 官方包/engine/*.dll        D:/ninfer/runtime/engine/   # 约 66 个（不要复制它的 ninfer-serve.exe）
cp vcpkg/installed/x64-windows/bin/*.dll D:/ninfer/runtime/engine/
cp build/apps/ninfer-serve.exe D:/ninfer/runtime/engine/
```

**依赖自检**（精简 PATH 跑 `--version`，缺什么 DLL 会直接报）：Windows 目录 + engine 目录之外
什么都不给，能打印版本就说明 DLL 链完整。也可用 PowerShell 的依赖分析工具核对导入表。

## 7. 步骤四：启动与调优

### 7.1 显卡选择陷阱（双 GPU 用户必读）

CUDA 默认按 **FastestFirst** 排序设备，与 nvidia-smi 的 PCI 总线序**相反**：

| 设备 | nvidia-smi 序号 | CUDA 序号 |
|---|---|---|
| RTX 4060 Laptop (8GB) | 0 | **1** |
| RTX 4070 Ti SUPER (16GB) | 1 | **0** |

所以启动前必须 `set CUDA_VISIBLE_DEVICES=0`（选 4070 TiS）。实测用 `--device 1` 引擎直接跑到了
笔记本卡上（日志可见 `calibrating ... rtx-4060-laptop-gpu-sm89 (24 SMs)`），8GB 卡装 11.3GB 权重
溢出到共享内存，被 strict 策略正确拒绝。**看启动日志里的 GPU 名字确认，别信参数。**

### 7.2 strict 显存策略与上下文上限（本机核心调优记录）

strict 策略逐块验证所有分配必须落在专用显存（防止 WDDM 静默借共享内存导致速度暴跌），启动时
从低到高探测 KV 池上限。实测过程：

| 尝试 | 结果 |
|---|---|
| `--max-context 131072`（128K，官方 S 档同款） | ❌ FATAL：`minimum Engine runtime reservation requires 5,279,317,248 bytes`——权重载入后仅剩 3.69GB，128K 的 rk8v4 KV 池最低要 5.28GB |
| `--max-context 81920`（80K） | ✅ strict 自动装满：**admitted 97,280 KV tokens**（比请求值还多 17K），14.85GB 驻留，余量 105MiB |

**结论：4070 Ti SUPER + 本套配置的物理上限 ≈ 97K KV tokens**（官方 5070Ti 软件包是 128K，
它的机器 CUDA 上下文开销更小）。逻辑上下文建议设 80K–93K，留出输出空间。

启动日志关键行（健康标志）：


### 7.3 完整启动命令（即本仓库 scripts 的成品 bat）

```bat
set CUDA_VISIBLE_DEVICES=0
ninfer-serve.exe "D:\ninfer\converted-models\Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.ninfer" ^
  --model-id qwen3.8-27b ^
  --max-context 81920 --prefill-chunk 256 ^
  --cuda-memory-policy strict --kv-dtype rk8v4 --host-cache-mib 6144 ^
  --default-max-tokens 0 ^
  --spec mtp --draft-tokens 4 --adaptive-mtp --lookup-ngram 31 ^
  --temperature 1 --top-p 0.95 --top-k 20 --min-p 0 ^
  --preserve-thinking --default-reasoning-effort xhigh ^
  --port 8081 --log-colours off
```

参数注释：`--model-id` 对外暴露的模型名（改成与你客户端一致，避免 404）；`--prefill-chunk 256`
与官方 S 档一致；`--host-cache-mib 6144` 是**主机内存**的上下文缓存池（不占显存）；`--spec mtp
--draft-tokens 4 --adaptive-mtp --lookup-ngram 31` = 官方 S 档同款投机解码；采样默认 temp 1 /
top-p 0.95 / top-k 20 / min-p 0。

### 7.4 日常调整速查

| 想调什么 | 改哪 | 注意 |
|---|---|---|
| 上下文长度 | `--max-context` | ≤97280；128 的倍数；超了启动即失败（安全失败） |
| 更长上下文 | `--kv-dtype rk4v4`（4bit KV，容量约翻倍） | 质量代价需自行实测 |
| 思考预算 | 加 `--default-thinking-budget N`（不设=无上限，仅受窗口约束） | 当前默认 effort=xhigh，客户端可按请求覆盖 |
| 借内存扩容 | `--cuda-memory-policy mixed` | ⚠️ 实测解码跌到 4.65 tok/s，仅应急 |
| 并发 | `--max-concurrency 1..8` | strict 下并发×KV 会挤爆 16GB，单用户保持 1 |
| 诊断 | `--device-profile calibrate` 重新校准 / `--log-level debug` | 校准结果缓存在用户目录，重装系统才需要重来 |

### 7.6 视觉版（图片/视频输入）

引擎原生支持 Vision，但有三道门槛，全部实测记录如下：

**门槛一：转换**。视觉权重来自独立的 mmproj GGUF（`mmproj-Qwen3.8-27B-BF16.gguf`，931MB BF16），
转换命令在文本版基础上改两处：`--components text,mtp,vision` + 追加
`--source "vision=D:/.../mmproj-...gguf"`；元数据还要**多补 2 个文件**（`preprocessor_config.json`
与 `video_preprocessor_config.json`，视频支持也要它）；venv 还要**多装 `gguf` pip 包**（视觉路线
的 mmproj 解析走官方包，文本路线则不需要）。产出 11.9GiB 制品（1176 张量，比纯文本多 333 个视觉
张量），耗时 58 秒。详见[模型转换指南](模型转换指南.md)第 8 节。

**门槛二：strict 策略是纯文本专属**。只要命令行出现 `--vision`（无论视觉塔放 GPU 还是 CPU），
引擎直接拒绝 mixed/strict：`--cuda-memory-policy mixed/strict requires one GPU, text-only
inference`。视觉版只能用 `default` 策略（无驻留保证，auto KV + 余量），牺牲掉 strict 的防溢出保护。

**门槛三：显存重算**。视觉塔如果驻留 GPU（`--vision-residency resident`，约 1GB），KV 池相应缩水；
本机实测视觉版的 KV 池水位（default 策略）：

| 尝试 | 结果 |
|---|---|
| `--max-context 65536` + headroom 768MiB | ❌ FATAL：KV 池要 3.31GB + 768MiB，超出权重后的 3.69GB 可用量 |
| `--max-context 49152`（48K） | ✅ KV 49,152 tok · runtime 2.66GiB · free 1.49GiB |

本仓库的取舍：**视觉塔放 CPU**（`--vision-residency cpu`，24 线程），零显存开销、图片编码慢些
（单图秒级到十几秒），换取与文本版几乎相同的显存预算。想换 GPU 塔加快编码：改
`resident` 并把上下文再降到 40K。

**实测**：256×256 纯红 PNG → 模型回答「红色」，prompt 130 tok（图片合并成约 76 个视觉 token），
全程 17.6s（含 xhigh 思考）。请求格式 = OpenAI 标准多模态消息（`image_url` + base64 data URI）。

启动模板：`scripts/start_qwen3_8_27b_ninfer_vision.bat`（与文本版同端口同模型名，二选一运行，
互相自动杀对方实例）。

| `.ninfer` 模型 | 直接复用 | 直接复用 | 直接复用 | 直接复用 |
| DLL 组装 | 直接复用 | 直接复用 | 用官方包自带 | 直接复用 |

### 9.2 显存上限的推算方法（任何卡通用）

启动日志的 `capacity | KV N tokens ... free X MiB` 给出当前值。改 `--max-context` 后 strict 探测
会给出真实上限：**FATAL 报错里的 `minimum Engine runtime reservation requires N bytes` 就是这一档
上下文的 KV 池需求**，减去当前 free 就是缺口，按比例缩 `--max-context` 再试，2–3 轮收敛。
（本机实测 52K 输入时 KV 池已含 MTP/ngram 工作区，不用自己扣。）

### 9.3 30 系（sm_86）额外说明

- CMake 参数仅改 `86`；nvprune 同理 `-arch sm_86`
- 引擎 CMakeLists 声明 80/86/89 走同一条 mma.sync 兼容路线，源码零改动
- 上游 3090 分支（iamwavecut/ninfer-all 整合线）有官方性能参考：27B 短对话 118 tok/s，
  可作为你的预期基准

## 10. 踩坑记录全集（35 条）

按实际遭遇顺序，每条含现象/根因/解法：

1. **GitHub 直连被墙**：443 超时。→ 浏览器走代理手动下载大文件 + 脚本级镜像回退（本仓库 fetch-asset.bat）
2. **git 走代理 TLS 握手失败**（`schannel: failed to receive handshake`）：Git for Windows 默认 schannel 后端与代理不兼容。→ `git -c http.sslBackend=openssl` 或 `export GIT_SSL_BACKEND=openssl`
3. **代理不转发大文件**：api.github.com 秒通，release/codeload 大文件 TLS 中途被掐（`error code 35` / `unexpected eof`）。→ 小文件直连可试，大文件一律走 gh-proxy.com 镜像前缀
4. **vcpkg.exe 下载地址**：bootstrap 脚本内嵌下载经常失败；且它发布在 **microsoft/vcpkg-tool** 仓库（不是 microsoft/vcpkg），版本号要取 `scripts/vcpkg-tool-metadata.txt` 里的 `VCPKG_TOOL_RELEASE_TAG`
5. **vcpkg 工具链缺件**：PowerShell Core 7.6.6 / 7zip / cmake 4.4.3 都是 vcpkg 首跑时按需下载的。→ 任一卡住就手动下载放进 `vcpkg\downloads\`，**文件名必须与 URL basename 完全一致**，哈希校验通过即命中缓存
6. **manifest 模式的 baseline 依赖 git 历史**：tarball 解压的 vcpkg 没有完整 git 对象，CMake 配置时报 `git show <sha>:versions/baseline.json failed`。→ 依赖装好后配置用 `VCPKG_MANIFEST_MODE=OFF`（classic），或 `git fetch --depth 1 origin <baseline-sha>` 补齐
7. **CMake 4.4.2 被拒**：`A suitable version of cmake was not found (required v4.4.3)`。→ cmake.org 直下 4.4.3 zip，解压后前置 PATH（vcpkg 会优先用系统 PATH 里够新版本的）
8. **vcpkg 资产缓存环境变量名**：是 `X_VCPKG_ASSET_SOURCES`（带 X_ 前缀）。写成 `VCPKG_ASSET_SOURCES` 不报错但**静默不生效**，下载全走默认源
9. **GitHub release 资产 ≠ git 归档**：meson-1.9.0.tar.gz 的 release 版和 archive/1.9.0.tar.gz **字节不同、哈希不同**；ffmpeg 9.0.2 的 vcpkg 输入也是 GitHub 标签归档（不是 ffmpeg.org 的 tar.xz）。→ 一切以 portfile 里的 SHA512 为准
10. **ffmpeg.org 官方包喂不进 vcpkg**：哈希门禁拒绝。→ 必须用 `github.com/ffmpeg/ffmpeg/archive/n9.0.2.tar.gz`
11. **classic vs manifest 混用**：classic 装依赖 + manifest 配置 = baseline 报错（同 #6）
12. **Git Bash 调 cmd 的引号地狱**：`cmd //c "D:\path\to\x.bat"` 被 msys 转义后 cmd 进交互模式空转（banner + 提示符，bat 根本没执行）。→ 在 Git Bash 里直接 `./x.bat` 执行
13. **bat 重定向假成功**：`> "%BUILD%\log"` 目标目录不存在时 cmd 打印"系统找不到指定的路径"、**命令不执行但 errorlevel 保持 0**，后续全部空转"成功"。→ 脚本开头 `if not exist` 建目录
14. **CUDA 算子编译 OOM 静默死**：`-j 22` 在 32GB 内存机器跑到 [602/653] 时编译进程被系统杀掉，**日志只有警告没有错误行**，ninja 只报 `subcommand failed`。→ 降 `-j 8` 续编（ninja 断点续编，不重做）
15. **CUDA 设备序与 nvidia-smi 相反**：CUDA 默认 FastestFirst，4070TiS 是 0 号（nvidia-smi 里是 1 号）。`--device 1` 直接把引擎送到了 4060 Laptop 上。→ 用 `CUDA_VISIBLE_DEVICES` 按位掩掉其他卡，并以启动日志的 GPU 名字为准
16. **strict 策略正确拒绝小卡**：8GB 的 4060 装 11.3GB 权重溢出共享内存，strict 在分配触碰时立刻 FATAL（`Shared GPU memory grew during device allocation touch`）——这是特性不是 bug，防的是静默掉速
17. **128K 在 16GB 卡上不是普适值**：官方 5070Ti 包的 S 档 128K 依赖它的机器开销；本机载入权重后 free 只有 3.69GB，128K KV 池最低要 5.28GB。→ 以 strict 探测为准（本机 97,280），别照抄官方参数
18. **模型名 404**：`--name`（转换时）决定的制品名 ≠ 客户端请求的 model 字段。→ 服务端加 `--model-id <客户端用的名字>`，零改客户端
19. **Git Bash 传中文 JSON 给 curl**：`curl -d '{"中文"...}'` 被 msys 转码后服务端报 `request body is not valid JSON`。→ 用 Python urllib 或 `curl -d @utf8.json`
20. **VCRUNTIME/编译器版本敏感**：MSVC v143 14.44.35207 是文档要求版本；低版本工具链编 nvcc 13.4 项目有未知风险，别用老 Build Tools 硬上
21. **bat 文件必须 ASCII-only**：UTF-8 中文注释在 GBK 码页的 cmd 下读成乱码，会把后面相邻的 `set`/`cd` 行一起撕碎——症状是"不是内部或外部命令"刷屏 + 变量为空 + 找不到 exe，且**没有任何编码报错**。→ bat 一律英文注释；必须中文则文件存 ANSI(GBK) 或 `chcp 65001` 配套
22. **strict 策略是纯文本专属**：`--cuda-memory-policy mixed/strict` 与 `--vision` 互斥（与视觉塔位置无关，引擎直接拒绝启动）。视觉构建只能用 `default` 策略 + `--kv-capacity auto --kv-headroom-mib N`
23. **视觉转换三件套**：mmproj 路线要多给 `preprocessor_config.json`、`video_preprocessor_config.json` 两个元数据文件 + venv 装 `gguf` pip 包（mmproj 解析走官方包，文本路线免装）；少一个就 FileNotFoundError/ImportError
24. **视觉版显存水位另算**：default 策略下 KV 池需求 ≠ strict 实测值（64K 档 FATAL 报 3.31GB + headroom）。降档公式：报错里的 KV 字节数 ÷ 65536 × 目标 tokens + headroom ≤ 权重后的 free，两轮收敛
25. **编译宿主 OOM 是静默死**：22 路并行 nvcc 在 32GB 内存机器跑到 602/653 时编译进程被系统杀掉，日志只有警告没有错误行，ninja 只报 subcommand failed。→ 降 -j 8 续编（ninja 断点续编不重做）
26. **bat 注释必须 ASCII-only**：UTF-8 中文注释在 GBK 码页 cmd 下撕碎相邻 set/cd 行（症状："不是内部或外部命令"刷屏 + 变量为空 + 找不到 exe，零编码报错）。→ bat 一律英文注释；必须中文则存 ANSI(GBK) 或 chcp 65001 配套
27. **Git Bash 调 cmd 的引号地狱**：`cmd //c "D:\\path\\x.bat"` 被 msys 转义后 cmd 进交互模式空转（banner+提示符，bat 根本没执行，exit 0 假成功）。→ Git Bash 里直接 `./x.bat` 执行
28. **bat 重定向假成功**：`> "%BUILD%\\log"` 目标目录不存在时命令不执行但 errorlevel 保持 0，后续全链空转"成功"。→ 脚本开头 mkdir
29. **长会话 agent 工具调用方言漂移**：~100K 会话中模型输出自造工具标记（`<|im_start|>function=...` 前缀污染 + 参数竖排碎裂），引擎解析失败合成 `malformed_tool_call` 占位 → 客户端报 unknown tool 连环失败。→ 防呆模板（KVMem 仓库 scripts/chat_template_strict.jinja，格式铁律随每请求注入）+ 关回灌 + presence 0
30. **--structured-output 与思考管线冲突**：开语法约束后深思全烧零输出（finish=length 无 content）；降思考档则 100% 工具调用变 malformed 占位（比不开更糟）。→ 此构建勿开
31. **客户端 max_tokens > KV 池 = invariant 崩溃诱因**：dsh 的 40,000 > 池 35,840 时输出租约拿不到页（#11 同族）。→ max_tokens ≤ 池 token 数；引擎侧配套修复为降级（KVMem 仓库门 3）
32. **思考预算 > max_tokens = 永远零交付**：budget 16384 + max_tokens 16000 ⇒ 思考等不到收束点就被硬截（症状 #2 实时复现）。→ budget < max_tokens，且两者都 ≤ 池
33. **token 密度估算坑**：英文技术行实测 ~35 token/行（不是 19）——构造测试题面/估会话规模按 1.8 倍系数修正，否则所有 K 级数字全错一档
34. **楔死引擎严禁 taskkill**：强杀楔死的 ninfer-serve 实测两次把 4070 Ti SUPER 整卡拖下线（PnP Unknown / 问题码 12 + 0xC0000138），管理员禁用/启用设备也失败，只能关机断电 30 秒冷启动。→ 楔死 = 直接冷启动，跳过杀进程
35. **"全 503 但 /v1/models 200" = worker 已死**：健康检查会骗人（#11 姊妹条）。→ 判活必须真发一条请求
